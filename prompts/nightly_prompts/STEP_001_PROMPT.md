# A01 — восстановить контракт gen_exporter_config.py -> YAML/DSN

## CONTEXT

Ты — внутренний coding-agent с доступом к рабочему репозиторию. Внешний инженер не имеет доступа к нему и будет проверять твой ответ перед следующим запуском. Не рассчитывай на историю предыдущих сессий.

Старый SQL-to-Prometheus exporter после перехода окружения на Python 3.12 падает с `ModuleNotFoundError: No module named 'sqlalchemy_aio'`. Wrapper `query-exporter.py` вызывает `query_exporter.main.script`. Рассматривается замена только runtime; решение ещё НЕ принято.

По сообщению владельца, `gen_exporter_config.py` читает XML серверов и watchlist, через pyodbc получает `exporter.meta_queries` и `exporter.meta_metrics`, создаёт `config_exporter.yaml` с разделами databases/metrics/queries и отдельные `.dsn`. Gradle запускает генератор примерно с `--input`, `--dir`, `--server`, `--watch` и копирует wrapper в пакет. Это ориентиры поиска, а не доказательство точного контракта.

## GOAL

Одна задача: статическим чтением восстановить фактический контракт генератора — какие YAML-поля и DSN он способен выдавать, из каких входов и с какими преобразованиями.

Это исследование генератора. Не требуется устанавливать все production-значения, анализировать весь проект или объяснять поведение стороннего runtime.

## SCOPE

READ-ONLY. DO NOT MODIFY ANY FILES.

1. Прочитай применимые инструкции репозитория. Укажи исходные Git HEAD, ветку и состояние рабочего дерева. Уже существующие изменения не трогай.
2. Найди `gen_exporter_config.py`. Если найдено несколько копий, установи используемую по узкому фрагменту Gradle, который её вызывает/пакует. Если однозначность недостижима в этом scope — остановись с BLOCKED.
3. Прочитай выбранный генератор целиком. Разрешено прочитать только прямо вызываемые локальные функции/константы/шаблоны, если они определяют его выход. Не обходи транзитивно весь проект. Отдельную крупную подсистему отметь как блокер для следующего исследования.
4. Из build.gradle/подключённого build-фрагмента прочитай только непосредственный вызов генератора и связанное копирование/переименование его результатов. Не анализируй весь deployment.
5. Если рядом уже есть подходящий безопасный пример выходного YAML, можно использовать один пример как иллюстрацию с указанием происхождения. Не ищи production-конфиги по всей файловой системе и не запускай генерацию ради примера.

Восстанови по коду:

- CLI-аргументы и defaults, входы, фильтры выбора server/database/watchlist, выходные файлы.
- Точные SELECT из meta_queries/meta_metrics; используемые поля/индексы, связи записей, фильтрацию. Полную схему таблиц сейчас не исследуй; не выводи её из `SELECT *` или обращения к нескольким полям.
- Все ключи YAML на каждом уровне, включая условные; источник значения, Python-тип до сериализации, defaults/условия отсутствия и точное преобразование. Если формат YAML собирается строками, укажи это и не приписывай данным неподтверждённые типы YAML.
- Правила именования database/query/metric, преобразования регистра, обрезания, замены, суффиксы и разрешение коллизий. Если поведение при коллизии следует из конкретной операции записи, покажи её. Не исправляй подозрительные имена.
- Полные объявленные mappings `obj_type` и `metric_type`, все видимые ветки обработки неизвестного значения. Разделяй «поддерживается генератором» и «реально используется».
- Обработку `run_interval`: исходное поле, тип/единицы, преобразование, default, пустые/NULL значения — только то, что видно по коду. Семантику интервала в runtime не угадывай.
- Как строятся списки query.metrics и query.databases; допускает ли именно генератор несколько БД у query и повторное использование metric. Не выводи поведение runtime из структуры списка.
- Есть ли пути генерации labels, параметров, expiration, autocommit, timeout и иных опций. Для отрицательного вывода укажи границу: «не генерируется в полностью прочитанных путях», а не «не используется в production».
- DSN: алгоритм имени файла и ссылки `file:...`, формирование URL/строки, кодирование и экранирование, имя драйвера, query options, кодировка/перевод строки/режим записи, если явно заданы. Разделяй запись ссылки генератором и её разрешение runtime. Не утверждай, что URL можно передать напрямую в pyodbc.
- YAML: используемый сериализатор/ручная сборка, параметры сериализации, порядок/перезапись записей, кодировка, если установлены. Наличие импорта не доказывает версию или доступность пакета в runtime.

## DO NOT

- Не создавай даже файл отчёта: верни Markdown только в ответе агента. Не меняй исходники, конфиги, lock-файлы и рабочее дерево; не делай commit/stash/reset/checkout.
- Не запускай и не импортируй генератор или модули проекта; не запускай Gradle, exporter, тесты, SQL, установку пакетов, сеть или подключения к БД.
- Не читай реальные XML с credentials, `.dsn`, `.env` и приватные ключи. Для структуры секретных данных используй код формирования. Если в исходнике есть литералы с секретами, не печатай их.
- Не выводи пароли, токены, credentials в URL/connection string, даже тестовые. Фрагменты с чувствительными литералами редактируй только в ответе, без записи на диск, и отмечай `[REDACTED]`; сохраняй имена ключей и алгоритм.
- Не исправляй обнаруженные дефекты, не предлагай патч, не проектируй runtime и не выбирай зависимости.
- Не изучай реализацию query-exporter, SQL views, полную metadata DDL, Prometheus/Grafana или systemd. Это следующие отдельные задачи.
- Не утверждай отсутствие feature во всём production на основании генератора или одного YAML.
- Не делегируй исследование параллельным агентам: текущий scope должен оставаться одним небольшим запуском.

## EXPECTED OUTPUT

Верни единый самостоятельный Markdown-отчёт `A01 — Generator contract` в сообщении, не файлом:

1. `STATUS: COMPLETE | PARTIAL | BLOCKED`; Git HEAD/ветка; начальное состояние дерева; точные исследованные пути; применимые инструкции; границы исследования.
2. Краткая подтверждённая цепочка «вход -> преобразование -> YAML/DSN».
3. Таблица `выходной путь/поле | вход/источник | преобразование | тип/default/условие | доказательство path:lines`. Включи все выходные YAML-поля, а не только известные из задания.
4. Полные mappings obj_type/metric_type и правила interval/naming/collisions; отдельная компактная таблица условных возможностей и границ отрицательных выводов.
5. Контракт DSN и файловой записи; никакого реального DSN с credentials.
6. Минимальные достаточные цитаты исходника с оригинальными номерами строк: чтение metadata, преобразования/построение YAML, DSN, сохранение и узкий Gradle-вызов. Таблица может ссылаться на эти цитаты. Не ограничивайся пересказом или номерами строк без проверяемого кода.
7. `UNKNOWN / BLOCKERS`: что не установлено, почему и какой минимальный файл/фрагмент нужен. Вопросы вне scope пометь как deferred; не пытайся решить их сейчас. Подозрение на дефект отделяй от подтверждённого поведения.
8. Выполненные команды, финальное состояние дерева и заявление о том, выполнялись ли записи/подключения/запуски кода. Если состояние изменилось без твоих действий, явно отметь это, не исправляй.
9. `HANDOFF`: task=A01, source revision, подтверждённые результаты, нерешённые вопросы, минимальный недостающий артефакт. Не начинай следующую задачу автоматически.

Не создавай синтетический YAML, выдавая его за фактический артефакт. Если примера нет, достаточно доказанного контракта из кода.

## ACCEPTANCE CRITERIA

- Однозначно установлен исследованный entrypoint и его связь с узким build-вызовом либо явно указан блокер.
- Все выходные поля и условные пути в выбранном генераторе покрыты; преобразования имеют path:lines и достаточные цитаты.
- Формирование имён, SQL, metric types, intervals, связей query/metric/database и DSN можно проверить по отчёту.
- Возможности генератора отделены от фактической production-конфигурации и от поведения runtime.
- Неизвестное отмечено явно; недостающие прямые helper-функции не заменены предположениями.
- Секреты не раскрыты; файлы не изменены; подключения и выполнение проекта не производились.

## STOP CONDITIONS

- Нет генератора, неоднозначны его копии или выбранная ревизия — вернуть BLOCKED с найденными путями и требуемым уточнением.
- Существенная часть вывода формируется недоступным helper/template или дальнейшее чтение требует анализа другой подсистемы — вернуть PARTIAL/BLOCKED с точно очерченным пробелом.
- Для продолжения нужны запуск кода, БД, зависимости, внешние ресурсы или изменение файла — не выполнять; описать минимальную отдельную проверку.
- Противоречивые источники — привести обе ссылки, не выбирать удобную версию молча.
- Найдена unrelated проблема — кратко отметить и не расширять задачу.

## COMMANDS / VALIDATION

Работай из уже предоставленного корня репозитория. Используй доступные read-only средства. Примеры для shell с git/rg (каждая команда отдельно, без перенаправления в файлы):

```sh
git --no-optional-locks status --short --untracked-files=normal
git rev-parse --show-toplevel
git rev-parse HEAD
git branch --show-current
rg --files -g AGENTS.md -g gen_exporter_config.py -g '*.gradle' -g '*.gradle.kts' -g '!build/**' -g '!venv/**' -g '!.venv/**'
```

После установления путей — точечный поиск строк вызова в выбранном build-файле (`rg -n 'gen_exporter_config|query-exporter\.py|config_exporter\.yaml' <проверенный build-файл>`) и чтение выбранных исходников с номерами строк. Не выполняй команды с буквальными placeholders. Не делай широкий `rg` содержимого всего репозитория и не печатай весь build-файл: там могут быть секреты. Используй средство чтения с редактированием чувствительных литералов до попадания в вывод; если оно недоступно и секреты нельзя безопасно исключить, верни блокер, не дамп исходника.

В конце повтори `git --no-optional-locks status --short --untracked-files=normal`. Если git/rg недоступны, используй штатные read-only инструменты агента; не устанавливай ничего. Чистое дерево не является предварительным требованием, но существующие изменения нужно сохранить и указать, если они влияют на исследованные файлы.
