Проанализируй текущую реализацию nightly automation в этом репозитории.

Архитектурное ограничение: центральный ai-zzzz содержит только список/пути подключённых проектов и универсальную оркестрацию. Вся project-specific логика, конфигурация, промпты, команды проверки и артефакты nightly automation должны оставаться внутри соответствующего проекта. Не переноси их в ai-zzzz.

Нужно доработать nightly workflow так, чтобы основной результат ночной работы был пригоден для быстрого утреннего просмотра без обязательного чтения git diff.

Спроектируй и реализуй минимальные изменения для следующего lifecycle:

ticket → implementation → project verification → independent AI review → optional fix → verification/review → final result

Требования:

каждый тикет выполняется изолированно;
результат каждого тикета сохраняется независимо от успеха или ошибки;
финальные статусы: READY, NEEDS_DECISION, BLOCKED, FAILED;
результат содержит краткое описание задачи, фактически выполненных изменений, результаты проверок, замечания reviewer, непроверенные аспекты и существенные риски;
отдельно отмечать изменения API, DB/schema, config и dependencies;
reviewer запускается с чистым контекстом и получает постановку задачи + итоговые изменения + результаты проверок, но не reasoning/transcript implementation-агента;
разрешён не более чем один автоматический цикл исправления замечаний reviewer;
если после него требуется содержательное решение человека, завершать NEEDS_DECISION, а не продолжать самостоятельно;
ошибка одного тикета не должна прерывать обработку остальных;
в конце ночного запуска формируется общий человекочитаемый report по всем тикетам;
подробные agent logs сохраняются отдельно и не должны быть основным morning report;
не добавлять UI, auto-merge, PR integration и другие функции, не необходимые для этого workflow.

Сначала изучи существующую архитектуру и максимально используй уже существующие механизмы. Не создавай параллельную систему рядом с имеющейся.

Перед изменениями дай короткий план:

что в текущей реализации уже подходит;
чего не хватает;
какие файлы/компоненты предлагается изменить;
какие новые сущности действительно необходимы;
как будет выглядеть lifecycle одного тикета и всего nightly run.

После этого реализуй изменения минимально необходимым способом. Не усложняй архитектуру ради будущих возможностей.
