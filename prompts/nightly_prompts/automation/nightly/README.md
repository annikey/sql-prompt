# Ночные запуски: Windows PowerShell 5.1 + корпоративный OpenCode

Общий модуль для ai-fosql. Не устанавливает OpenCode/Node, не меняет сертификаты,
ExecutionPolicy, корпоративную авторизацию или глобальные настройки агента.

## Как выглядит работа

Днём вы с агентом готовите тикеты и планы. Разрешённые на ночь строки помечаете
night-ready и сохраняете в Git. В отдельном worktree должна быть именно эта версия
кода и документации. Ночью запускается очередь: одна задача — одна новая сессия.
Утром вы читаете отчёт, проверяете diff и принимаете результат.

Для нескольких проектов используется один локальный JSON. Порядок — по одному
готовому тикету из каждого проекта, затем следующий круг. Одновременно работает
только один агент. Лимит maxTasks общий на весь прогон, в примере — 3.

Это не обязательно «одна задача за ночь»: после успешной проверки обвязка автоматически
берёт следующую разрешённую задачу. На первой ошибке или блокере останавливает весь прогон.

## 1. Положить модуль в ai-fosql

Скопируйте automation/nightly из архива в корень ai-fosql.
Существующие skills и прежний optional-task-workflow-package не заменяются.
Ночной контракт отличается: очередь двигает скрипт, а не агент; чекбокс закрывает человек.
Не подключайте одновременно противоречащие инструкции про автоматическое закрытие тикетов.

| Файл/папка | Назначение |
|---|---|
| Invoke-Nightly.ps1 | Очередь проектов, блокировка, лимиты, общий отчёт |
| Run-OneTicket.ps1, Worker.ps1, Common.ps1 | Внутренняя реализация; не запускать отдельно |
| Test-NightlySetup.ps1 | Проверка установки, путей, Git, очередей |
| New-NightlyWorktree.ps1 | Создание нового worktree без перезаписи существующих |
| Register-NightlyTask.ps1 | Регистрация ежедневного задания Windows |
| prompts/ | Планирование, реализация, ночной контракт, дневная подготовка, review |
| examples/ | Конфигурация, очередь, документ тикета, проектный verifier |
| tests/ | Тесты очереди, синтаксиса PS и управления дочерним процессом |
| workflows/ | Описание полного цикла |
| local/ | Ваши настройки и журналы; игнорируется Git |

## 2. Проверить установленный CLI

В обычном Windows PowerShell под рабочим пользователем:

```powershell
Get-Command opencode.cmd | Select-Object Source
opencode --version
opencode run --help
opencode models
```

Нужны run, --file, --format, --model и --agent. Используется уже установленный
корпоративный CLI; версия npm-пакета в Nexus может отличаться от публичной.
Пакет не переустанавливает и не обновляет CLI.

Запишите точный provider/model корпоративной модели. Не используйте случайную
модель по умолчанию и не переносите токены/пароли в ai-fosql.
Если команда opencode.cmd не найдена, укажите её полный фактический путь.
PATH Node/nvmx настраивается в extraPath, а не угадывается скриптом.

## 3. Подготовить каждый рабочий проект

1. Создайте docs/nightly-plan.md по examples/nightly-plan.md.
2. Создайте документы тикетов по ticket.template.md; перенесите в них исходные требования.
3. По согласованию добавьте фрагмент examples/AGENTS.optional.md в проектные правила.
4. Для реализации создайте .ai/verify-nightly.ps1 по примеру и замените его тело
   реальными проверками вашего проекта. Шаблон намеренно завершается ошибкой:
   он не должен создавать ложный «зелёный» результат.
5. Сохраните очередь, документы, правила, verifier и нужный код в Git.

Скрипт проверки получает ProjectPath и TicketId. Его exit 0 означает, что ВСЕ
обязательные автоматические проверки завершены успешно. При ошибке команды
немедленно передавайте ненулевой код. Не заканчивайте скрипт успешной командой после
неудачного теста. Отсутствующий стенд — ошибка/блокер, а не пропуск с exit 0.

Для режима plan проверочный PS-скрипт не нужен; поле verificationScript можно оставить "".
Автоматическая проверка реализации выполняется один раз после агента.
Починки после неудачного прогона тестов автоматически не повторяются.

### Формат очереди

Каждый тикет — одна строка, порядок полей фиксированный:

```markdown
- [ ] TASK-101 | mode=implement | status=night-ready | doc=docs/tickets/TASK-101.md | depends=-
- [ ] TASK-102 | mode=plan | status=night-ready | doc=docs/tickets/TASK-102.md | depends=TASK-101
```

ID уникален в проекте: буквы, цифры, дефис, подчёркивание. Зависимости разделяются
запятыми; отсутствие — дефис. Межпроектные зависимости в этой версии не поддерживаются.
Очередь — отдельный файл: произвольные чекбоксы шагов держите в документах тикетов.
Некорректные строки, неизвестные зависимости и циклы останавливают запуск.

| Статус | Значение |
|---|---|
| draft | Подготовка; ночью не брать |
| night-ready | Человек разрешил выполнение |
| running | Выполняется; после аварии требует ручного разбора |
| ready-for-review | Агент закончил; для implement verifier вернул 0; нужна приёмка |
| blocked | Агент сообщил, что требуется решение/доступ |
| failed | Ошибка CLI, результата, проверок или ограничений |
| done + [x] | Человек принял результат |

Только человек переводит результат в done и закрывает [x].
Для реализации в документе тикета должна быть отдельная строка:

```markdown
<!-- plan-approved -->
```

Маркер добавляйте только после просмотра плана; не вставляйте его в общий шаблон.
После ночного планирования человек читает план, добавляет маркер и меняет ту же строку
на mode=implement, status=night-ready. Новый план не превращается в реализацию ночью сам.

По умолчанию зависимости требуют done. Если явно включить allowVerifiedDependencies,
ready-for-review задачи режима implement тоже разблокируют зависимые задачи.
Это разрешает строить цепочку на ещё не принятом человеком коде.
Результат планирования такого права не даёт даже с этим переключателем.

## 4. Подготовить отдельный worktree

Пример команд с условными путями и именем вашей дневной ветки:

```powershell
.\automation\nightly\New-NightlyWorktree.ps1 -Repository "D:\work\project-a" -Destination "D:\work\nightly\project-a" -Branch "ai/nightly" -BaseRef "feature/my-ticket"
```

Параметры обязательны: базовая ветка не выбирается наугад. Источник должен быть
чистым, каталог назначения и новая ветка не должны уже существовать.
Скрипт создаёт локальную ветку и checkout одного указанного коммита, ничего не публикует.

Worktree — отдельные файлы/индекс, но общая история, refs и Git-конфигурация.
Это не песочница и не защита от вредоносных команд. Он также не копирует
незакоммиченные/игнорируемые файлы, локальную БД, зависимости и окружение.
Подготовьте их штатным способом без переноса production-доступов.

Для существующего чистого worktree обновление выполняете явно днём, например:

```powershell
git -C "D:\work\nightly\project-a" merge --ff-only feature/my-ticket
```

Если fast-forward невозможен — разберите ветки вручную. Обвязка не делает reset,
stash, rebase, clean или принудительную синхронизацию.

## 5. Заполнить локальную конфигурацию

В ai-fosql:

```powershell
New-Item -ItemType Directory -Path .\automation\nightly\local -Force
Copy-Item .\automation\nightly\examples\nightly.local.example.json .\automation\nightly\local\nightly.local.json
```

Не повторяйте Copy-Item поверх уже настроенного файла. Измените:

- repoPath, worktreePath, expectedBranch для каждого проекта;
- точный корпоративный model;
- contextFiles — реальные проектные инструкции (минимум AGENTS.md);
- allowedEditPaths — только разрешённые каталоги кода, тестов и документов;
- verificationScript — проектный скрипт проверок;
- openCodeCommand и extraPath при нестандартной установке;
- ночное окно и лимиты.

Все относительные пути в общем JSON разрешаются относительно самого JSON.
queuePath, contextFiles и verificationScript — относительно worktree.
Шаблоны allowedEditPaths используют / и *; не допускается разрешить весь репозиторий
одним "*". Для режима plan изменять можно только текущий документ и машинный результат.

Чтобы добавить проект, добавьте ещё один объект в projects со своим id и путями.
Все проекты используют общую очередь запуска, лимит задач и logRoot.
Не делайте несколько независимых расписаний с разными logRoot на те же worktree.

sharedInstructionFiles позволяет явно передать тексты уже существующих skills
из ai-fosql (относительно JSON, например ../../../skills/project-docs-update/SKILL.md).
По умолчанию список пуст: неизвестное содержимое ваших skills пакет не подменяет.
Связанные references при необходимости тоже добавьте в список. Обычный автоматический
вызов навыков и подагентов ночью отключён; инструкции здесь передаются как текст.

### Полномочия и корпоративный провайдер

В дочерний процесс передаётся отдельный агент ai-fosql-night через
OPENCODE_CONFIG_CONTENT. Разрешены чтение/поиск и ограниченное редактирование;
shell, внешние каталоги, MCP-инструменты, веб и делегирование запрещены.
--auto не используется. Sharing выключен. Корпоративные provider/auth настройки
из штатных файлов не заменяются.

Если OPENCODE_CONFIG_CONTENT уже задан вашим корпоративным окружением, запуск
останавливается: нужно согласованно объединить настройки, а не затереть провайдера.
Постоянные запреты организации не следует ослаблять ради ночного запуска.

Права инструментов зависят от версии CLI. До живого запуска проверьте их с вашей
корпоративной сборкой: что новый агент применяется и недопустимая операция отвергается.
runtimeApproved=false — предохранитель. После просмотра конфигурации и правил
поставьте true для ручного smoke-test, затем проверьте его до включения расписания.

Важная граница: разрешение запускать verifier — это разрешение исполнять код проекта,
в том числе изменённые агентом тесты. Сам verifier защищён от правок агента, но это
не делает тесты безопасными автоматически. Используйте изолированные локальные тестовые
данные и минимальные права. Worktree/промпт/allowlist не заменяют OS-песочницу.
Также проверьте штатные плагины OpenCode: запрет tools не запрещает код плагина при старте.

## 6. Проверить днём

Из ai-fosql:

```powershell
.\automation\nightly\tests\Test-Queue.ps1
.\automation\nightly\tests\Test-Worker.ps1
.\automation\nightly\Test-NightlySetup.ps1 -ConfigPath .\automation\nightly\local\nightly.local.json
.\automation\nightly\Invoke-Nightly.ps1 -ConfigPath .\automation\nightly\local\nightly.local.json -DryRun
```

Первые два теста не используют модель. Второй запускает и останавливает локальную
заглушку процесса. Test-NightlySetup вызывает только --version и run --help,
не делает inference, но старт самого CLI может задействовать штатные плагины.
DryRun проверяет очередь и показывает первую доступную задачу каждого проекта,
без изменения задач и запросов модели; может создать каталог журналов/lock-файл.

Для первой живой проверки оставьте одну небольшую mode=plan задачу, maxTasks=1,
установите runtimeApproved=true и запустите:

```powershell
.\automation\nightly\Invoke-Nightly.ps1 -ConfigPath .\automation\nightly\local\nightly.local.json -Manual
```

-Manual обходит только время суток, но сохраняет таймауты, согласования и ограничения.
Проверьте реальный расход именно в корпоративной квоте. Успешный запуск CLI сам по себе
не подтверждает нужный биллинг. Далее проверьте один implement с вашим verifier.
После smoke-test верните нужное maxTasks и разберите/сохраните созданные изменения.

## 7. Включить расписание

```powershell
.\automation\nightly\Register-NightlyTask.ps1 -ConfigPath .\automation\nightly\local\nightly.local.json -WhatIf
.\automation\nightly\Register-NightlyTask.ps1 -ConfigPath .\automation\nightly\local\nightly.local.json
```

Создаётся ai-fosql-nightly: ежедневно, в startTimeLocal, под текущим пользователем,
без повышения прав. Существующее задание не перезаписывается.
При корпоративном запрете регистрации обратитесь к администраторам.
Скрипты не меняют ExecutionPolicy; при блокировке нужен штатный механизм разрешения/подписи.

Время берётся на Windows-машине, где зарегистрировано задание, не на телефоне
и не обязательно на домашнем компьютере. При RDP это удалённая рабочая машина.
Узнайте точные границы восьмичасовых интервалов: 02:05 в примере — не установленный факт.

Учётная запись должна оставаться вошедшей в Windows. Блокировка экрана или отсоединение
RDP обычно сохраняют сеанс; Sign out завершает его. Корпоративная политика может
завершать отключённые сеансы — это нужно проверить. Машина должна быть включена,
не спать, иметь питание и доступ в корпоративную сеть.
Скрипт не включает пробуждение и догоняющий запуск пропущенного задания.

Проверка с заблокированным экраном: запустите задание через Task Scheduler днём
на временном тестовом ночном окне. Одна лишь проверка -Manual не проверяет планировщик.

## 8. Остановка и восстановление

STOP-файл останавливает текущий управляемый процесс и не даёт запускать новые задачи:

```powershell
New-Item -ItemType File -Path .\automation\nightly\local\STOP -Force
```

Здесь путь совпадает с примером stopFile. Если меняли его — используйте свой.
Остановка не откатывает изменения. Не удаляйте STOP до разбора результатов;
когда готовы продолжать, удалите только этот файл вручную.
Для приостановки расписания можно отключить ai-fosql-nightly в Планировщике.

На таймауте обвязка завершает только свой worker и его дочерние процессы.
Она не завершает все node/opencode на машине. Уже отправленный запрос провайдеру
может продолжить обработку и тарификацию даже после остановки локального процесса.

Живой прогон не начинается, если worktree грязный. running после аварии не повторяется
автоматически. Сначала просмотрите изменения и логи, затем осознанно поменяйте статус
и сохраните состояние. Автоматических retry и очистки старой работы нет.

## 9. Утром: приёмка и следующая ночь

В local/nightly-logs/latest-run.txt находится путь к последнему запуску.
В нём report.md и summary.json; по каждому тикету — state.json, prompt.md,
agent/stdout.log, agent/stderr.log, verification/ при наличии,
cumulative.diff и untracked-files.txt. Журналы могут содержать рабочий код:
не публикуйте их и не коммитьте в общую библиотеку.

cumulative.diff — накопительный diff относительно HEAD; он не включает содержимое
новых неотслеживаемых файлов. Их список сохранён отдельно, сами файлы остаются в worktree.
Изменения предыдущих задач видны следующей сессии как код и документы, но не история чата.

1. Откройте worktree в редакторе, изучите отчёт, git status и фактические изменения.
2. Для принятых тикетов вручную поставьте done и [x]. Для неполных сохраните честный статус.
3. Выполните обычный локальный commit принятых изменений. Служебную .ai-night-run/
   не добавляйте: выбирайте файлы для staging явно, без слепого git add -A.
4. Перенесите результат в дневную ветку обычным review/merge-процессом команды.
5. Подготовьте новую очередь, сохраните дневные изменения и явно обновите ночную ветку.

В рабочем проекте можно заранее добавить .ai-night-run/ в .gitignore или локальное
исключение Git. Сам пакет это не делает и не удаляет старые файлы.
Для будущей ночи worktree должен быть чистым, кроме этой служебной папки.

## Ограничения лимита и совместимости

- Скрипт ограничивает число задач, длительность каждой сессии/проверки, весь прогон
  и время окончания окна. Он НЕ измеряет корпоративные 25 млн и не знает остаток
  общей квоты: для этого нужен официальный API вашего шлюза. Оставляйте запас.
- Провайдерская ошибка/лимит или ошибка OpenCode завершает прогон; бесконечного
  перезапуска нет. Внутренние retry CLI ограничиваются внешним таймаутом.
- Одна проектная очередь, один worktree и одна ветка на проект; нет параллельных
  агентов и межпроектных атомарных операций.
- Git-контроль обнаруживает изменённые отслеживаемые и новые неигнорируемые файлы;
  это аудит после действия, не гарантия отсутствия иных эффектов.
- На машине автора архива нет Windows PowerShell: реальные Windows-тесты
  и корпоративный OpenCode не запускались. См. VALIDATION.md.

## Проверенные публичные интерфейсы

Использованные интерфейсы run/--file/--format/--model/--agent описаны в
[CLI OpenCode](https://opencode.ai/docs/cli/).
Настройки прав — в [Permissions](https://opencode.ai/docs/permissions/),
runtime-конфигурация — в [Config](https://opencode.ai/docs/config/).
Это не подтверждение совместимости с вашей конкретной версией из Nexus.
